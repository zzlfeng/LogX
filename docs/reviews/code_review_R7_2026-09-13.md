## 四、本次新发现问题

### 4.1 P3 — 60KB 上限仍存一处**死常量**，与"统一单源"的声称不符

`core/src/format.cpp:49-51`：

```cpp
struct UserRecordHeader {
    static constexpr uint32_t kMaxTag = 64;
    static constexpr uint32_t kMaxMsg = 60 * 1024;  // 配合 64KB 单条上限
    ...
};
```

**引用计数核查**：全仓库（`*.cpp`/`*.h`）检索 `kMaxMsg` → **零引用**；`UserRecordHeader` 亦**从未被用作类型**（仅其自身定义内的 `tag[kMaxTag]` 引用了一个成员）。即该结构体是纯文档性声明，`kMaxMsg` 为**死常量**。

**为何仍值得记录**：
1. **与 R7-4 的声称矛盾**。提交信息称"60KB 上限统一单源"，但此处仍留存第二份 `60 * 1024`，且命名（`kMaxMsg`）与注释（"配合 64KB 单条上限"）**会让人误以为它掌管 msg 上限**。
2. **语义本身不准确**：真实约束是 `user_total = 27 + tag + msg ≤ 60KB`，故 msg 单独**不可能**达到 60KB；此常量作为"msg 上限"在语义上偏松/失实。
3. **风险**：未来维护者若修改 `kMaxMsg` 以为在调整上限，将**毫无效果**（死代码），而真正的门槛在 `kMaxUserPayload`。

**建议**：删除该死常量（或改为引用 `kMaxUserPayload` 并修正注释口径），使"60KB 单源"名副其实。

### 4.2 P3（hygiene）— CHANGELOG 曾提交字面占位符

提交 `471466a` 将 `| \`<R7>\` |` 写入提交表的哈希列。虽在下一提交即修正，但该提交**贡献为零且引入畸形行**：`<R7>` 非合法哈希，任何检出至 `471466a` 的读者会看到表格中出现非空非哈希的单元格。

需注意：`9c84c5d` 与该提交**时间戳相同**（13:52:13），说明修正目标哈希当时已存在——**占位符本可避免**（此前各轮均为"先有 fix 提交、再补真实哈希行"，如 `3d111bc`/`43d359a`/`1b515ff`）。

**建议**：保持既有模式（fix 提交后再补行），或将该行并入 fix 提交；避免占位符入库。
