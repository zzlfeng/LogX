## 三、发现项详述

### D-1（P3）`sum_raw_len_since` 修复注释引入与实现不符的"块损坏→false"契约

- **位置**: `core/include/logx_internal.h:240-241`（提交 `9ad0db3` 新增）；对照 `core/src/flusher.cpp:912-976`
- **现象**: 新注释称："out_last_block_* 输出最后一个有效块的起止偏移；**文件 IO 或块损坏失败返回 false**（调用方按长度异常处理）。契约保证：返回 false 时，*out_bytes 与 *out_last_block_* 均重置为 0。"
- **实现事实（行级）**:
  - 返回 `false` 的路径**仅两条**：`file_open` 失败（`flusher.cpp:920`）、`sz < kFileHeaderSize`（`:922-924`）。
  - **块损坏不返回 false**：块头不可解析（`:935-938`）、payload 短读（`:945-946`）、CRC 不符（`:947-948`）、加密 tag 短读（`:955-956`）均为 `block_valid = false → break → return true`（`:959`、`:975`），此时 `*out_bytes` 携带**已累计的部分和**、两个偏移出参为最后一个**有效**块的起止（`:968-969`）。循环内 header/payload 的读 IO 短读同样 `break → return true`。
  - 新注释的**后半句**（"返回 false 时出参归零"）正确：入口 `:916-918` 清零，且两条 false 路径此后不再触碰出参。
- **触发链**: 未来调用方按新注释编码——把 `false` 当作"文件不可解析"信号、并默认"返回 true 即全块有效"——会对"损坏→true + 部分和"的真实路径产生错误预期（例如漏掉对部分和的二次校验）。当前生产消费者 `recovery.cpp:221-234` 不读偏移出参、只消费 `sum` 且有水位防御，**现网无行为影响**。
- **后果**: 文档级。属于"修复注释型发现时引入了新注释错误"，正是 R13 §9.5 失误模式 5（出参未追消费者）的镜像。
- **修法**: 改为如实两段式，例如："`out_last_block_*` 输出最后一个有效块的起止偏移；仅文件打开失败或文件小于 32B 文件头时返回 false（此时三个出参均为 0）；循环内遇块损坏或短读则提前终止并返回 true，出参携带终止前的部分累加结果（宁丢不脏，与 scan_one 纪律一致）。"
- **需补测试**: 无（注释级，无行为变化）。

### D-2（P3，用户裁决残余）N-1 以"方案 B"文档化收口，C API 侧配置陷阱残余

- **位置**: `core/src/logx_c.cpp:292-301`（本轮未改动）；`core/include/logx_c.h:33`、`android/kotlin/LogX.kt`（本轮改动）
- **现象与界定**: R13 §9.4 对 N-1 的建议修法是"C 侧 3 行 fail-fast 下界（<97 → INVALID_ARG）+ `kMaxTag` 上提 + 改写 `test_flusher.cpp:1262-1306` + Kotlin 补下界"。本轮经用户裁决（CHANGELOG R13 批次条目 2 原文"按用户选定'方案 B'：保持当前运行时防御设计"）**不实施** fail-fast，改为：`logx_c.h:33` 注释统一（此点同时关闭了 N-5 与 C-7 指出的"契约矛盾"成分，因新口径已如实描述"截断到空记录仍放不下"）+ Kotlin KDoc 建议 `>= 97`（算术 27+64+6 正确）+ `require(config.maxLogLength > 0)`。
- **残余风险（须留痕）**: C API 调用方（非 Kotlin）传 `max_log_length ∈ [1, 96]` 仍可落入必然丢弃工作点：`[1,32]` 对**任何** tag（含空 tag）必丢（`format.cpp:208-210`，需 `max_total ≥ 33 + tag_len`）；`[33,96]` 对 `tag_len > max_log_length − 33` 的记录必丢。丢弃路径对调用方可见（同步返回码 + `LOGX_EV_DROP` + `drop_too_large` 计数，`logx_c.cpp:443-447`），且 C 头文件契约文本现已准确——故残余为**已文档化的可用性陷阱**，非隐蔽缺陷。另注：Kotlin `require(>0)` 与 C 侧 `==0 → INVALID_ARG`（`logx_c.cpp:292`）基本重复，仅新增拦截 Kotlin 负数穿 JNI 后回绕为巨大 uint32 的路径（该路径原本也会被 `> kMaxRecordTotal` 拦截），防御价值有限但无害。
- **术语澄清（一并记录）**: 本批"方案 B"（维持运行时行为 + 文档对齐）**不是** R13 §2.4 的"方案 (b) 截 tag 而非丢整条"。两处文档（CHANGELOG 条目 2、R13 §11.1）均只写"方案 B"未展开定义，建议后续文档补一句定义以免与 §2.4(b) 混淆。
- **修法（二选一）**: (i) 维持裁决，则在 `logx_c.h:33` 或 `logx_open` 注释处给 C 调用方补一句"建议 ≥ 97（用户头 27B + 最大 tag 64B + 片头 6B）"与 Kotlin 对齐，并在计划表 Backlog 记一笔"C 侧下界 fail-fast：用户裁决暂不实施"；(ii) 若改主意实施 fail-fast，按 R13 §9.4 序 2 全套执行（含 `test_flusher.cpp:1262-1306` 连带改写——该用例本轮确认未动，方案 B 下继续有效）。
- **需补测试**: 方案 (i) 无；方案 (ii) 见 R13 §2.5 + §9.4（`tag_len × max_log_length` 二维扫描，此维度至今仍缺，见 C-16 残留）。

### D-3（P3）N-4 未按发现闭环：替代性守卫落地，TLS 内存总账注释仍缺

- **位置**: `core/src/format.cpp:300`（新增守卫，`c84dca1`）；`core/src/format.cpp:123-128`、`:282`（未改动）
- **现象**: R13 §9.3 N-4 的发现本意是"同线程 TLS ≈124KB（64KB scratch + 60KB trunc_buf），Android 再 +≤64KB，**注释未记总账**"；C-10 修订建议为"注释上界应按 ≈124KB/线程 记账"。本轮落地的是 `trunc_buf` 拼装前容量守卫 `if (prefix_len + marker_len > sizeof(trunc_buf)) return kInvalidInput;`——相关但**不是**同一诉求。
- **守卫本身复核（属实且正确）**: 静态不可达（`format.cpp:231-234` static_assert 钉死 61440 ≥ 61410，余量 30B；`prefix_len ≤ user_total ≤ kMaxUserPayload`、`marker_len ≤ sizeof(marker)-1`，和不可能溢出 uint32）；触发时 `kInvalidInput → kBuildRecordsInvalidInput → LOGX_ERR_INVALID_ARG`（`flusher.cpp:830-831`）显式可见，非静默丢弃；与全文件既有"防御:不可达"风格一致（`:296` 同款）。**有独立加固价值，予以保留。**
- **缺口仍在**: 全仓 grep `124KB`（含 `124 KB`）0 命中；`format.cpp:123-128` 的 scratch 注释仍只有动机论证（FM-03），未记"同线程 scratch 64KB + trunc_buf 60KB ≈124KB 常驻、N 线程 ×124KB、Android 另 +≤64KB"总账。P3-1 自 R13 起即要求该记账，本轮以替代改动销号属于收口口径漂移。
- **修法**: 在 `format.cpp:128` 注释末补一句总账（约 2 行）：如"内存总账: 本函数 TLS scratch 64KB + format_record_bounded 的 trunc_buf 60KB，同线程常驻 ≈124KB（N 线程即 ×N）；Android/JNI 侧另有 tls_payload_buf ≤64KB（logx_jni.cpp:366-368）。"
- **需补测试**: 无（注释级）。运行期确认项沿用 R13 §9.6（实际常驻内存量未实测）。
