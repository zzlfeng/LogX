## 三、本次新发现问题

### 3.1 P3 — `recovery.cpp` 5 处同概念裸 `6` 未转换，「6B 全量单源化」声称不成立

`core/src/recovery.cpp` 存在与 `flusher.cpp` **逐行对应**的裸 `6`：

| `recovery.cpp` | 对应 `flusher.cpp`（R9-2 已转换） | 概念 |
|---|---|---|
| `:37 if (total - off < 6) return 0;` | `:37 if (total - off < kHeaderLen)` | 记录头长度 |
| `:39 uint32_t sz = 6 + len;` | `:41 sz = kHeaderLen + len` | 头+载荷 |
| `:59 if (total - pos < 6) {` | `:53 if (total - pos < kHeaderLen)` | 记录头长度 |
| `:67 for (i = 0; i < 6; ++i)` | （6B 全零终止符判定） | 记录头长度 |
| `:91 cksum1(raw + pos + 6, payload_len)` | （载荷起点=跨过 6B 头） | 记录头长度 |

**可行性与影响**：`recovery.cpp:21` 已含 `logx_internal.h` → 后者含 `logx_format.h`（`:19`），故 **`kHeaderLen` 在该 TU 本就可见，转换无需新增包含**——属**纯遗漏**。

**后果**：
1. 提交声称「R9-2 … 6B 单源声称完全成立」与 CHANGELOG R9-2 节「**全量扫描**发现 flusher.cpp 另有 5 处…R8 文档"6B 全部单源"的声称至此才完全成立」**均失准**——`recovery.cpp` 的 5 处仍在。
2. **同类问题第三次复现**（R8-3 块内部分替换、R9-1 补 staging、R9-2 补 flusher 却漏 recovery），说明当前"逐文件人工扫描"的收敛方式不可靠。

**建议**：将 `recovery.cpp` 上述 5 处一并绑定 `kHeaderLen`；并考虑以「`6` 作为记录头长度的字面量」为模式做一次全仓库（含 tests）穷尽排查。

### 3.2 观察（根因）— `flusher.cpp` 与 `recovery.cpp` 存在平行重复实现

- `recovery.cpp:36-42 probe_record` ⟷ `flusher.cpp:35-44 peek_record_len`（记录长度探测，语义几乎相同）
- `recovery.cpp:54+ ring_scan` ⟷ `flusher.cpp:50+ split_impl`（raw 流按记录边界扫描/切分）

**同一扫描逻辑存在两份实现**，正是常量单源化反复遗漏的结构性根因——在一处统一无法覆盖另一处。建议后续评估将记录扫描原语收敛为共享实现（置于 `logx_format.h`/`.cpp`），从根上消除该类漂移。

`core/include/logx_internal.h:219` 注释：`raw_len ∈ [6, kSingleRecordMaxRaw]`。其对应实现 `flusher.cpp:312` 已改为 `kHeaderLen`，注释未同步（仅文档层面，无功能影响）。
